# ADR-0020: 타겟 언어 기본값을 '자동'으로 두고, 방향은 원문에서 해석한다

- **Status**: Accepted ([ADR-0021](0021-explicit-source-language.md)이 개정 — 원문 언어도 명시 선택 가능해졌고, `resolveTargetLanguage`는 `resolveDirection`으로 대체됐습니다)
- **Date**: 2026-08-12
- **관련**: `src/utils/detectLanguage.ts`, `src/components/editor/EditorCanvasTipTap.tsx`, `src/desktop/oddeyesAppBridge.ts`, `src/ai/translateDocument.ts`

## Context

타겟 언어는 타겟 패널 헤더의 Select 하나로만 정해졌고, 값은 `project.metadata.targetLanguage`에 문자열로 박혔습니다. 한 번 고르면 그 뒤로 아무도 원문과 대조하지 않습니다.

**이 구조에서 나던 결함:**

- **번역이 자기복사가 됩니다.** `translateDocument.ts`의 시스템 프롬프트는 `srcLang`이 리터럴 `'Source'`이고 타겟만 메타데이터에서 옵니다. 국문 원문인데 타겟이 `한국어`로 남아 있으면 프롬프트가 "Source에서 한국어로 번역하세요"가 되고, 모델은 원문을 거의 그대로 되받아씁니다. 프롬프트 안에 방향을 검증할 재료가 없습니다.
- **검수는 한쪽만 자동이었습니다.** `ReviewPanel`은 `sourceLanguage`를 `detectSourceLanguage()`로 감지하면서 `targetLanguage`는 메타데이터를 그대로 씁니다. 둘이 어긋나면 그 불일치가 검수 프롬프트에 그대로 들어갑니다.
- **오염된 값이 외부 에이전트까지 갑니다.** `oddeyesAppBridge`의 `getStatus`/`getTranslationContext`가 저장값을 그대로 내보내므로, MCP로 붙는 에이전트의 방향 교차검증이 같은 값을 정답으로 믿습니다. 원천이 하나라 가드가 가드 역할을 못 합니다.

### 감지가 이 조합에서 신뢰 가능한 이유

기존 `detectSourceLanguage`는 비율 임계(한글 30%, 라틴 50%)인데, KO↔EN 판정에는 **비율보다 "한글이 있는가"가 훨씬 강한 신호**입니다. 영문 문서의 한글은 0%지만, 영어 용어가 범벅인 국문 문서도 한글이 5% 밑으로는 잘 안 내려갑니다. 이 비대칭 덕분에 L10N 표처럼 두 언어가 섞인 문서에서도 임계가 안정적입니다. 반대로 일본어·중국어까지 자동으로 결정하려 들면 근거 없이 오탐이 늘어납니다.

### 검토한 대안과 버린 이유

- **감지해서 값을 자동으로 채운다(보정형).** 원문 로드 시 타겟이 비었거나 원문과 같으면 반대 언어로 세팅하고 "되돌리기" 토스트를 띄우는 안. 새 상태를 만들지 않고 MCP 계약도 그대로라는 장점이 있지만, **사용자가 손으로 고른 값을 앱이 몰래 바꾸는 동작**이라 "직접 고른 값인가"를 추적하는 플래그가 따라붙고, KO→KO 다듬기 같은 의도적 동일언어 작업과 싸웁니다.
- **바꾸지 않고 충돌만 막는다(가드 전용).** 원문과 타겟이 같으면 차단만 하는 안. 오판이 0이지만 **수동 선택 자체가 그대로 남아** 원래 문제(매번 골라야 하고, 고르면 아무도 재검증 안 함)를 풀지 못합니다.
- **6개 언어 전부 자동 판정.** 스페인어·러시아어까지 감지하려면 문자 체계로는 부족해 stopword 수준의 언어 식별이 필요합니다. 실제 사용은 KO↔EN이 압도적이라 비용 대비 이득이 없습니다.

## Decision

**Select에 '자동' 항목을 넣어 기본값으로 삼고, 저장값은 센티널(`'auto'`)로 두되 방향은 쓰는 시점에 원문에서 해석한다. 명시 선택일 때만 동일언어 가드를 건다.**

- **해석은 `resolveTargetLanguage(stored, sourceText)` 한 곳** (`src/utils/detectLanguage.ts`). 저장값이 `'auto'`거나 비어 있으면 `detectSourceLangCode`로 원문을 보고 반대 언어를 돌려주고(국문→`영어`, 영문→`한국어`), KO/EN이 아니면 `null`을 돌려 호출부가 명시 선택을 요구하게 합니다.
- **`metadata.targetLanguage`를 프롬프트·MCP로 흘리는 경로는 전부 이 함수를 거칩니다** — 번역·폴리싱·선택 재번역·검수·채팅 프롬프트·정렬 뷰 헤더·브리지 2곳. 거치지 않으면 센티널 문자열이 그대로 프롬프트에 박힙니다.
- **브리지는 저장값이 아니라 해석값을 내보냅니다.** `'auto'`를 그대로 주면 외부 에이전트의 방향 교차검증이 통째로 꺼지므로, MCP 계약상 `targetLanguage`는 "해석된 방향"이고 `null`은 "설정으로도 원문으로도 결정 못 함"을 뜻합니다.
- **비교는 언제나 `normalizeLang()`을 거칩니다.** Select 값은 한글 라벨(`'한국어'`), 감지 함수 반환값은 영문명(`'Korean'`)이라 문자열끼리 비교하면 가드가 영원히 안 걸립니다.
- **자동이 무엇으로 풀렸는지 Select 라벨에 드러냅니다**(`자동 (영어)`). 깜깜이 자동은 오설정만큼 위험합니다.

## Consequences

- **얻은 것**: 기본 경로에서 방향을 고르는 조작이 사라졌고, 스테일 값이 구조적으로 생기지 않습니다. 저장값이 센티널이라 "예전에 골라둔 언어"가 다음 문서에 따라붙지 않습니다.
- **얻은 것**: 명시 선택이 원문과 같으면 번역 전에 막힙니다. 자동으로 푼 값은 정의상 원문의 반대라 이 가드에 걸릴 수 없으므로, 가드는 사용자가 직접 고른 경우에만 작동합니다.
- **얻은 것**: 외부 에이전트가 받는 `targetLanguage`가 앱이 실제로 쓰는 방향과 같아졌습니다.
- **잃은 것 / 감수하는 것**: **라틴 문자 원문은 전부 영어로 간주합니다.** 스페인어 원문이면 자동이 `한국어`를 고르고 경고 없이 진행합니다. 실사용이 KO↔EN이라 감수하며, 다른 언어 원문은 명시 선택이 정답입니다.
- **감수하는 것**: 일본어·중국어 원문에서는 자동이 아무것도 결정하지 않고 "타겟 언어를 직접 선택하세요" 토스트로 막습니다. 종전의 "타겟 언어를 선택하세요"와 같은 자리에서 같은 행동을 요구합니다.
- **따라오는 의무**: `metadata.targetLanguage`를 새로 읽는 코드를 추가할 때는 반드시 `resolveTargetLanguage`를 거칩니다. 날값을 읽으면 센티널이 새고, 문자열로 비교하면 표기 체계 두 개(`'한국어'` vs `'Korean'`)에서 조용히 어긋납니다.
