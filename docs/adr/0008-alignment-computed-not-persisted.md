# ADR-0008: 문단 정렬은 계산하고 저장하지 않는다

- **Status**: Accepted
- **Date**: 2026-07-28
- **관련**: `src/utils/alignUnits.ts:116`, `src/components/editor/AlignmentView.tsx`, `design_handoff_oddeyes_editor_ui/PHASE_4_5_alignment_view.md`

## Context

원문↔번역문을 문단 단위로 나란히 보는 대조 뷰가 필요했습니다. 원래 계획(Phase 4-3 세그먼트 인스펙터)은 `segmentGroupId`로 원문 블록과 번역 블록이 연결돼 있다고 전제했습니다.

전제가 틀렸습니다:

- `segments` 테이블과 `project.segments` 모델은 존재하지만, `projectStore` **내부에서만 참조되고 외부 호출자가 없습니다.** 즉 실제 문서 편집이 세그먼트를 갱신하지 않습니다 — 죽은 모델입니다.
- 에디터가 붙이는 `translationUnitId`는 Source/Target 두 인스턴스에서 **독립적으로 발급**됩니다. 같은 id가 같은 문단 쌍을 뜻하지 않습니다.

따라서 선택지는 둘이었습니다.

- **영속 정렬을 제대로 만든다** (Phase 5) — 스키마 추가, 편집 시 정렬 갱신, 정렬 깨짐 복구 UI까지 4–6주 규모. 그런데 **정렬 자동 계산이 얼마나 잘 맞는지 데이터가 없는 상태**에서 착수 판단을 할 수 없었습니다.
- **매번 계산한다** — 저장하지 않으므로 스키마 변경이 0이고, 틀린 정렬이 데이터로 굳지 않습니다.

## Decision

**뷰를 열 때마다 계산하고, 결과를 저장하지 않는다.** 읽기 전용으로 한정한다.

- `alignUnits`가 시그니처(`type:depth:level`) 시퀀스 LCS로 계산. 짝이 안 맞는 구간은 **고치지 않고 불일치로 표시**한다 (1:1 / 1:0 / 0:1만 지원, 1:N 미지원)
- 재계산 트리거는 `onUpdate`가 아니라 **300ms 디바운스된 문서 JSON 스냅샷**. 스펙이 제안한 리비전 해시 비교는 markdown 변환+해시가 `alignUnits`보다 싸지 않아 채택하지 않음
- **에디터를 언마운트하지 않는다** — 정렬 뷰는 `PanelGroup` 위 오버레이이고 문서 보기는 `visibility:hidden`으로 가린다. 언마운트하면 TipTap 인스턴스가 파괴돼 `editorStore`가 비고 점프·검수 적용이 깨진다. `display:none`이 아니라 `visibility`인 이유는 ① 레이아웃이 남아 스크롤 위치가 보존되고 ② 숨은 요소는 포커스를 못 받아 읽기 전용이 함께 강제되기 때문 (React 18이라 `inert` 사용 불가)
- 이슈·코멘트 배지는 `segmentGroupId`(신뢰 불가) 대신 **텍스트 포함 검사**로 매핑한다 (`useAlignmentAnnotations.ts`). 여러 유닛에 걸리면 매핑하지 않고 하단에 `위치를 특정하지 못한 이슈 N건`으로 모은다
- **Phase 4-3은 폐기한다.**

## Consequences

- **얻은 것**: 스키마 변경 없이 대조 뷰를 얻었습니다. 자동 정렬이 틀려도 잘못된 데이터가 저장되지 않으므로, 실패의 비용이 "이 화면이 부정확하다"에서 멈춥니다.
- **잃은 것 / 감수하는 것**: 1:N 정렬을 표현할 수 없고, 사용자가 정렬을 수동으로 고칠 수 없습니다. 뷰 진입마다 재계산 비용이 듭니다.
- **의도된 부산물**: 매핑 실패 건수와 정렬 리포트(`alignmentReport.ts`가 `AlignResult` 요약을 JSONL 한 줄로 내보냄)의 `ratio`가 **Phase 5 착수 판단의 근거**입니다. ratio가 0.95 이상이면 영속 정렬은 불필요하고, 0.7 근처면 착수 가치가 있습니다. 자동 수집은 하지 않으며 사용자가 버튼으로 내보냅니다.
- **따라오는 의무**: Phase 5를 시작하기 전에 리포트를 실제로 모아 보아야 합니다. 데이터 없이 착수하면 이 ADR이 피한 함정으로 되돌아갑니다.
