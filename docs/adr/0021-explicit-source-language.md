# ADR-0021: 원문 언어도 명시 선택 가능하게 하고, 방향은 한 함수로 해석한다

- **Status**: Accepted
- **Date**: 2026-08-26
- **개정**: [ADR-0020](0020-auto-target-language.md)
- **관련**: `src/utils/detectLanguage.ts`, `src/components/editor/EditorCanvasTipTap.tsx`, `src/ai/prompt.ts`, `src/ai/chat.ts`, `src-tauri/src/models.rs`

## Context

ADR-0020은 타겟 언어를 '자동' 기본값 + 센티널로 정리했지만, **원문 언어는 손대지 않았습니다.** 원문은 저장되지 않고 매번 텍스트에서 추정되며, 어디에도 표시되지 않고, 사용자가 고칠 방법이 없습니다. 그 비대칭에서 나던 결함:

- **복사본에 방향이 굳습니다.** `duplicate_project`가 `target_language`를 그대로 복사하는데, 명시값이면 `resolveTargetLanguage`가 감지를 건너뜁니다. EN→KO 프로젝트를 복사해 원문을 국문으로 갈아끼우면 방향이 KO→KO로 남아 모델이 원문을 되받아씁니다. 사용자에게는 "원문을 아직 영어로 안다"로 읽힙니다. 원문 언어가 화면에 없으니 무엇이 틀렸는지 알 방법도 없습니다.
- **채팅 프롬프트에 방향이 아예 없었습니다.** `chat.ts`는 토큰 최적화로 `sourceDocument`를 넘기지 않는데(`undefined`), `prompt.ts`가 바로 그 필드를 방향 판정 표본으로 썼습니다. 결과적으로 자동 타겟 프로젝트의 채팅 시스템 프롬프트는 **언제나** `언어: Source → Target`이었습니다. ADR-0020이 "채팅 프롬프트도 해석기를 거친다"고 적은 경로는, 거치되 빈 문자열을 받고 있었습니다.
- **원문 언어 자리가 리터럴이었습니다.** `prompt.ts`·`translateDocument.ts`가 `'Source'`를 박아, ADR-0020이 지적한 "프롬프트 안에 방향을 검증할 재료가 없다"의 나머지 절반이 남아 있었습니다.
- **검수는 청크마다 방향이 갈렸습니다.** `ReviewPanel`이 청크 앞 3개 세그먼트로 매번 재감지해, 영문 문서 중간의 국문 인용 하나로 같은 검수 안에서 모순된 방향이 프롬프트에 실렸습니다.

## Decision

**원문 언어도 타겟과 같은 모양(저장 + 센티널 `'auto'` + 헤더 Select)으로 올리고, 두 값의 해석을 `resolveDirection` 하나로 합친다.**

- **`resolveDirection({ source, target }, sourceText)`가 유일한 해석 지점**입니다. `resolveTargetLanguage`는 삭제했습니다. 원문이 명시 선택이면 자동 타겟은 **텍스트를 다시 감지하지 않고 그 값을 뒤집습니다.**
- **선택 인자가 아니라 필수 구조체로 받습니다.** `resolveTargetLanguage(stored, text, source?)` 같은 형태는 호출부 하나만 빠뜨려도 타겟이 조용히 텍스트 재감지로 되돌아갑니다 — ADR-0020의 "따라오는 의무"는 산문이라 강제력이 없었고, 이번에는 컴파일 에러로 만듭니다. `ProjectMetadata`를 통째로 받지 않는 것도 의도적입니다: 호출부가 스칼라 두 개만 스토어에서 고를 수 있어야 `updatedAt` 갱신 때마다 리렌더가 번지지 않습니다.
- **판정기 둘을 각각 한 가지 일만 시킵니다.**
  - `detectSourceLangCode`(한글 존재 5%, 4,000자) — **방향을 고르는** 데만. ADR-0020 그대로 KO/EN만 답합니다.
  - `detectDominantLangCode`(비율 30%, 500자) — **번역을 막는** 데만. 종전 `detectSourceLanguage`의 임계·표본을 그대로 물려받았습니다.
- **표시·프롬프트용 원문 라벨은 `방향 판정기 ?? 보수 판정기`** 순으로 뽑습니다. 방향 판정기를 먼저 보는 이유는 **라벨이 실제로 쓰이는 방향과 어긋나면 안 되기 때문**입니다 — 영어 용어가 범벅인 국문 문서에서 보수 판정은 '영어'인데 방향은 ko→en이라, 라벨만 보수 판정으로 띄우면 헤더가 "영어 → 영어"로 읽힙니다. 보수 판정은 방향 판정기가 기권하는 일본어·중국어에서만 내려옵니다.
- **채팅은 `sourceSample`을 따로 넘깁니다.** `sourceDocument`에 넣으면 프롬프트에 문서가 통째로 인라인되어(`formatDocument`) 토큰 최적화가 무너집니다. 방향을 싣는 것과 문서를 싣는 것은 별개의 결정입니다.
- **검수는 실행당 한 번 방향을 풉니다** (앞 50개 세그먼트).

### 왜 `detectSourceLangCode`를 넓히지 않았나

일본어·중국어까지 답하게 넓히면 `kana >= 5%`가 먼저 걸려, **일본어를 몇 줄 인용한 한국어 문서가 'ja'로 확신**됩니다. 지금은 `null` → "직접 선택하세요"라는 안전한 결말인데, 넓히면 자신 있는 오답이 되고 새 원문 불일치 가드까지 오작동시킵니다. 판정기는 그대로 두고, 일·중 거부를 **뒤집기 단계**로 옮기는 편이 낫습니다.

### 왜 차단 가드에 보수 판정기를 쓰나

방향 판정기의 한글 5% 임계는 방향을 *고르는* 데는 안전 쪽이지만, 차단에 쓰면 오탐이 곧 차단이 됩니다. 구체적으로: 한국어 용어가 몇 개 섞인 영문 원문 + 타겟 명시 `한국어`는 정당한 EN→KO 작업인데, 방향 판정기는 원문을 'ko'로 보고 동일언어 가드를 발동시킵니다. 종전에는 비율 기반 `detectSourceLanguage`가 이 자리에 있어서 문제가 없었고, 그 성질을 그대로 보존해야 회귀가 없습니다. 단위 테스트가 이 케이스를 고정합니다.

### 검토한 대안과 버린 이유

- **복제 시 언어를 `'auto'`로 리셋한다.** 스테일 값의 원천을 끊지만, 같은 문서를 복제하는 정상 사용례에서 매번 다시 고르게 만듭니다. 어긋남은 이제 헤더에 보이고 가드가 잡으므로 **원본 그대로 복사**를 유지합니다.
- **판정기를 하나로 합친다.** "두 판정기가 답이 갈린다"는 그 자체로는 결함이 아니라 **서로 다른 질문에 답하기 때문**입니다("무슨 언어인가" vs "막을 만큼 확실한가"). 합치면 둘 중 한쪽 호출부가 반드시 손해를 봅니다.
- **원문 불일치를 경고만 하고 진행한다.** 사용자가 겪은 증상이 정확히 "잘못된 방향으로 번역이 나감"이라, 경고만으로는 처방이 되지 않습니다.

## Consequences

- **얻은 것**: 방향이 두 패널 헤더에 항상 보이고, 틀리면 한 번의 클릭으로 고쳐집니다. 원문 언어가 프롬프트에 실려 모델이 방향을 교차검증할 재료를 갖습니다.
- **얻은 것**: 채팅 시스템 프롬프트가 처음으로 실제 방향을 담습니다(종전 `언어: Source → Target`).
- **얻은 것**: 검수 한 번에 방향 하나. 청크별로 갈리지 않습니다.
- **얻은 것**: 브리지가 `sourceLanguage`도 해석값으로 내보내, 외부 에이전트의 방향 교차검증이 양쪽을 다 봅니다(필드 추가라 기존 계약은 유지).
- **잃은 것 / 감수하는 것**: **명시 원문이 KO/EN이 아니면 자동 타겟이 `null`입니다.** 원문을 `일본어`로 고르면 타겟도 직접 골라야 합니다. ADR-0020이 이미 감수한 "근거 없이 뒤집지 않는다"의 연장입니다.
- **감수하는 것**: **방향이 풀리지 않을 때 막는 것은 전체 번역뿐입니다.** `openTranslatePreview`만
  `checkDirection`을 태우고, 문서 폴리싱·선택 재번역·선택 폴리싱은 `?? 'Target'`으로 진행합니다 —
  그 경우 프롬프트에 `You are a professional translator into Target.` 같은 문장이 실립니다.
  ADR-0020의 "호출부가 명시 선택을 요구하게 한다"를 세 경로는 따르지 않는 셈이지만, 실사용이
  KO↔EN이라 `resolveDirection`이 `null`을 돌려주는 경우가 없어 **막는 대신 기록으로 둡니다**
  (2026-09-03 프롬프트 감사 F10). 되살릴 조건은 KO/EN 밖 원문을 실제로 다루기 시작할 때입니다.
- **감수하는 것**: 새 원문 불일치 가드는 **명시 선택에서만** 작동합니다(자동은 정의상 자기 자신과 모순될 수 없습니다). 한글이 30% 넘게 섞인 문서를 원문 `영어`로 명시해 두면 막힐 수 있고, 그때는 Select를 `자동`으로 되돌리면 됩니다.
- **따라오는 의무**: 방향을 새로 읽는 코드는 반드시 `resolveDirection`을 거칩니다. 차단 판단에는 `detectDominantLangCode`를, 방향 결정에는 `detectSourceLangCode`를 씁니다 — 바꿔 쓰면 정당한 번역이 막힙니다.
