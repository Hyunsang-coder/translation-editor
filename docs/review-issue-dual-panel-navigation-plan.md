## 1. 한눈에 보는 결론

이번 기능의 핵심은 **두 패널에 동일한 `scrollTop`을 적용하는 것**이 아니다. 원문과 번역문은 문장 길이, 줄바꿈, 글꼴, 줄 높이, 표 구조가 다르므로 각 패널에서 이슈에 대응하는 앵커를 별도로 찾고, 각 스크롤 컨테이너에서 앵커를 최상단으로 이동해야 한다.

최종 목표는 다음과 같다.

1. 검수 이슈 카드에서 이슈를 클릭하거나 `본문에서 보기`를 누르면 해당 이슈의 위치로 이동한다.
2. 정렬 화면의 `이슈 N개` 표시를 누르면 그 정렬 단위에 연결된 첫 번째 이동 가능한 이슈로 이동한다.
3. 일반적인 이슈는 번역문을 의미상의 기준점으로 삼되, 원문도 같은 이슈의 원문 구간 또는 대응 단위로 함께 이동한다.
4. 원문 누락/번역문 추가처럼 한쪽 발췌문이 없는 이슈는 텍스트가 존재하는 쪽을 기준으로 삼고, 반대쪽은 대응 단위가 확실할 때만 이동한다.
5. 원문과 번역문은 **서로 독립적으로** 계산하여 각각의 이슈 앵커가 패널 상단에 오도록 한다.
6. 현재 사용자가 조정한 패널 너비는 이슈 클릭 때문에 자동으로 바꾸지 않는다. 패널 너비 동일화는 비교 편의 기능으로 별도 과제로 둔다.

## 2. 사용자에게 보이는 기대 결과

### 2.1 검수 이슈 카드에서 이동

검수 패널에서 특정 이슈 카드를 클릭하거나 카드의 `본문에서 보기`를 누르면 다음 순서로 동작한다.

1. 선택한 이슈를 활성 이슈로 기록한다.
2. 현재 정렬 화면이라면 문서 편집 화면으로 전환한다.
3. 원문 패널에서 원문 이슈 구간 또는 확실한 대응 단위를 찾는다.
4. 번역문 패널에서 번역문 이슈 구간 또는 확실한 대응 단위를 찾는다.
5. 두 패널을 각자의 계산 결과에 따라 부드럽게 스크롤한다.
6. 각 패널에서 찾은 앵커의 상단이 해당 패널의 상단 여백 아래에 오도록 한다.

카드의 최상단 이동은 에디터 이동과 별개의 보조 동작이다. 카드 목록 내부에 해당 카드가 존재하면 카드도 목록 영역 안에서 보이도록 이동한다. 카드가 현재 심각도 필터에 의해 숨겨져 있으면 사용자의 필터를 자동으로 바꾸지 않고, 에디터 이동만 수행한다.

### 2.2 정렬 화면의 이슈 표시에서 이동

정렬 화면의 한 행에 여러 검수 이슈가 연결될 수 있으므로 현재 UI의 `이슈 N개` 집계 표시를 그대로 개별 이슈 선택 UI로 간주하지 않는다.

- 1차 구현에서는 집계 표시를 버튼으로 바꾼다.
- 버튼을 누르면 해당 정렬 단위에 연결된 미해결 이슈 중 문서 순서상 첫 번째 이동 가능한 이슈를 선택한다.
- 정확한 특정 이슈를 선택하려면 검수 패널의 개별 이슈 카드를 사용한다.
- 같은 행의 여러 이슈를 정렬 화면에서 각각 선택하는 UI는 후속 개선 범위다.

이 기준은 현재 `이슈 N개`가 숫자만 표현하고 있다는 UI 형태를 크게 바꾸지 않으면서, 클릭 결과를 결정적으로 만들기 위한 것이다.

### 2.3 양 패널이 모두 표시되는 경우

원문·번역문이 분할 표시된 일반 모드에서는 두 패널 모두 이동한다. 두 패널의 스크롤 위치나 이동량이 같을 필요는 없다. 사용자는 같은 이슈를 양쪽에서 동시에 확인할 수 있고, 줄바꿈이 달라도 각 패널의 관련 구간이 상단에 놓인다.

### 2.4 한 패널만 표시되는 경우

포커스 모드, 원문 전용 모드, 번역문 전용 모드에서 이슈를 눌렀을 때 숨겨진 패널을 강제로 다시 열거나 패널 너비를 변경하지 않는다.

- 현재 화면에 표시되는 패널만 이동한다.
- 숨겨진 패널은 대응 앵커 계산을 시도할 수 있지만 DOM 위치 측정과 스크롤은 수행하지 않는다.
- 사용자의 보기 모드를 클릭 하나 때문에 암묵적으로 변경하지 않는다.

이 동작은 숨겨진 패널을 갑자기 다시 열어 작업 흐름을 깨는 부작용을 막기 위한 것이다. 나중에 `양쪽 패널에서 보기` 같은 명시적인 동작을 추가할 수는 있지만 이번 범위에는 포함하지 않는다.

## 3. 현재 구조와 조사 결과

### 3.1 검수 패널과 이슈 목록

대상 파일: `src/components/review/ReviewPanel.tsx`, `src/components/review/ReviewResultsTable.tsx`

- `ReviewResultsTable`이라는 이름이지만 실제로는 카드 목록 UI다.
- 실제 목록 스크롤 컨테이너는 카드들을 감싸는 내부 `overflow-y-auto` 영역이다.
- 현재 카드는 `data-issue-id`를 갖지 않으므로 DOM 기반 카드 이동을 위해 식별자를 추가해야 한다.
- 현재 `본문에서 보기`는 `ReviewPanel.handleViewInDocument`로 연결된다.
- 기존 이동 로직은 번역문 에디터에서 `resolveSuggestionRange`로 범위를 찾고 선택·포커스만 수행한다.
- 기존 로직에는 원문 패널 이동과 앵커를 패널 최상단에 맞추는 처리가 없다.
- 검토 중 화면과 완료 화면에서 `ReviewResultsTable` 전달 props가 다르므로 두 분기 모두 새 이동 콜백을 연결해야 한다.
- `ReviewPanel`은 활성 사이드바 패널일 때만 마운트된다. 정렬 화면에서 검수 패널을 열어야 하는 경우 마운트 이전 요청을 보존할 수 있는 일회성 상태가 필요하다.

### 3.2 정렬 화면

대상 파일: `src/components/editor/AlignmentView.tsx`, `src/components/editor/AlignmentRow.tsx`, `src/components/editor/useAlignmentAnnotations.ts`

- 정렬 결과는 `alignUnits`와 정렬 연산을 바탕으로 계산된다.
- 각 행에는 이슈 개수와 최상위 심각도가 표시된다.
- 현재 이슈 표시는 `span`이며 클릭 동작이 없다.
- `AlignmentRow` 전체는 행 선택을 위해 클릭 가능하므로 이슈 버튼에는 이벤트 전파 차단이 필요하다.
- `useAlignmentAnnotations`는 현재 이슈 개수만 제공한다. 양방향 이동을 위해 행별 `issueIds`도 함께 제공해야 한다.
- 현재 annotations 계산 경로는 해결된 이슈를 포함할 가능성이 있다. 검수 패널의 `getAllIssues()`와 동일하게 미해결 이슈만 사용하도록 기준을 통일해야 한다.
- 정렬 화면은 읽기 전용 오버레이이며, 문서 편집기는 `visibility: hidden` 상태로 계속 마운트되어 있을 수 있다. 정렬 화면에서 문서 화면으로 전환한 뒤 DOM 좌표를 측정하려면 최소 한 번의 렌더 프레임을 기다려야 한다.

### 3.3 에디터와 스크롤 컨테이너

대상 파일: `src/components/editor/EditorCanvasTipTap.tsx`, `src/index.css`, `src/components/editor/SearchHighlight.ts`

- 실제 ProseMirror 문서 영역이 `height: 100%; overflow: auto`인 스크롤 컨테이너다.
- 소스와 타깃 에디터는 각각 별도의 scroll container를 가진다.
- 현재 `alignCounterpartScroll`은 선택한 번역 단위를 상대 패널에 맞추는 기능이다. 이 기능은 한 번에 보이는 단위 중심이며, 특정 검수 발췌문을 양쪽 최상단에 배치하는 기능과 목적이 다르다.
- 현재 위치 맞춤 구현은 보이는 후보만 제한하여 LCS 계산량을 줄이는 최적화가 있다. 이 최적화를 제거하지 않는다.
- 메인 영역에는 전역 `zoom`이 적용될 수 있다. 화면 좌표와 `scrollTop` 보정 시 `editorZoom`을 고려해야 한다.
- 검색 하이라이트에 실제 스크롤 가능한 조상을 찾고 zoom을 보정하는 참고 로직이 있다. 새 기능은 이 원칙을 재사용하되, 검수 이슈 앵커에 맞는 API로 분리하는 것이 좋다.

### 3.4 이슈·범위 매칭 유틸리티

대상 파일: `src/components/review/reviewApply.ts`, `src/editor/utils/alignedCounterpartUnits.ts`, `src/editor/extensions/TranslationUnitId.ts`

- `ReviewIssue`에는 `sourceExcerpt`, `targetExcerpt`, `segmentGroupId`, `segmentOrder`가 있다.
- `findExcerptRange()`는 정규화된 텍스트, 인용부호 제거, 단위 범위, 중복 매칭에 대한 fail-closed 처리를 제공한다.
- `resolveSuggestionRange()`는 적용할 `suggestedFix` 길이를 이용하는 보정 경로가 있으므로 단순 위치 이동의 기본 함수로 재사용하지 않는다.
- `findAlignedCounterpartUnits()`는 translation unit ID를 우선 사용하고, 필요한 경우 LCS 정렬로 대응 단위를 찾는다.
- 대응 매핑이 부분적으로만 성립하거나 모호하면 빈 결과를 반환하는 fail-closed 정책이 이미 있다. 검수 이동도 임의 위치로 추측하지 않고 같은 정책을 따른다.
- `collectTranslationUnits()`와 `data-translation-unit-id`를 사용하면 텍스트가 여러 ProseMirror 노드에 걸친 경우에도 단위 수준의 안전한 fallback을 만들 수 있다.

## 4. 용어와 기준점 정의

### 4.1 이슈 앵커

이슈 앵커는 특정 패널 안에서 스크롤 기준으로 사용할 위치다. 다음 세 가지 상태를 구분한다.

| 상태 | 의미 | 스크롤 기준 |
| --- | --- | --- |
| `exact-range` | 해당 패널의 발췌문을 고유하게 찾음 | 찾은 텍스트 범위의 시작 위치 |
| `unit-range` | 발췌문은 직접 못 찾았지만 대응 translation unit을 찾음 | 대응 단위의 시작 위치 |
| `none` | 신뢰할 수 있는 위치를 찾지 못함 | 스크롤하지 않음 |

`exact-range`가 항상 가장 우선이다. `unit-range`는 정확한 발췌문을 찾을 수 없을 때만 사용한다.

### 4.2 의미상의 기준 패널

기준 패널은 하나로 고정하지 않는다.

- 양쪽 발췌문이 모두 있는 일반 이슈: 번역문이 의미상의 주 기준이다. 다만 실제 이동은 원문과 번역문 각각 독립적으로 수행한다.
- 원문 누락 또는 번역문이 비어 있는 이슈: 원문이 기준이다.
- 번역문에만 추가된 이슈: 번역문이 기준이다.
- 한쪽 발췌문이 존재해도 그쪽 위치를 직접 찾지 못하면, 다른 쪽의 직접 매칭 또는 대응 단위가 확실한 경우 이를 활용한다.

여기서 “번역문이 기준”이라는 말은 번역문 `scrollTop`을 원문에도 복사한다는 뜻이 아니다. 의미적으로 어느 텍스트가 이슈를 대표하는지에 대한 우선순위이며, 두 패널의 실제 좌표는 별도로 계산한다.

### 4.3 이동 성공의 정의

두 패널을 모두 이동해야만 성공으로 간주하지 않는다.

- 한쪽 앵커만 확실하면 확실한 쪽만 이동한다.
- 반대쪽에 위치를 추측해서 잘못된 문장을 보여주지 않는다.
- 양쪽 모두 `none`이면 현재 위치를 유지하고 사용자에게 위치 특정 실패를 알릴 수 있다.
- 이동 후 selection이나 focus가 필요한 경우에도 선택 동작이 스크롤 계산을 덮어쓰지 않도록 순서를 고정한다.

## 5. 상세 동작 사양

### 5.1 이슈 카드 클릭

기본 동작은 카드의 모든 빈 영역 클릭을 이동으로 사용할 수 있다. 단, 카드 내부의 다음 조작은 카드 이동을 중복 실행하지 않는다.

- 체크박스
- 적용
- 복사
- 무시
- 링크 또는 버튼

카드 자체에 `data-issue-id="..."`를 부여하고, 카드 클릭 콜백은 `issueId`를 전달한다. 개별 버튼은 기존 동작을 유지하며 필요하면 `stopPropagation()`으로 카드 클릭을 막는다.

접근성 기준:

- 카드 전체를 클릭 대상으로 만들 경우 키보드 Enter/Space도 동일하게 동작시킨다.
- 단순히 클릭 가능한 `div`로 만들지 말고, 버튼 또는 명시적인 `role`, `tabIndex`, 키보드 처리 중 하나를 사용한다.
- 이동 버튼에는 `aria-label`을 제공한다.
- 이동 중에는 포커스가 검수 패널에 남아도 되며, 에디터 포커스로 강제 이동하는 동작은 기존 UX와 충돌하지 않는지 확인한다. 기본값은 위치 이동 후 타깃 에디터에 포커스하는 현재 동작을 유지하되, 실제 키보드 작업 흐름을 검증한다.

### 5.2 정렬 행의 이슈 버튼

`AlignmentRow`의 이슈 배지는 다음 기준으로 변경한다.

- 이슈 개수가 0이면 버튼을 표시하지 않는다.
- 이슈 개수가 1 이상이면 기존 숫자 표시를 유지한 버튼으로 렌더링한다.
- 버튼에는 `aria-label="이슈 N개 본문에서 보기"`에 해당하는 번역 키를 사용한다.
- 버튼 클릭은 행 선택을 발생시키지 않는다.
- 버튼 키보드 조작도 마우스 클릭과 동일한 이동 콜백을 호출한다.
- `issueIds[0]`을 이동 대상으로 사용한다.

`issueIds`의 순서는 문서 순서로 고정한다. 보통 검수 패널의 `getAllIssues()`가 반환하는 순서를 사용하고, 같은 단위에 여러 이슈가 있으면 `segmentOrder`, 결과 순서, 안정적인 issue ID 순서가 일관되도록 정렬한다. 배열이 비어 있으면 숫자 배지는 표시하지 않거나 이동을 실행하지 않는다.

### 5.3 정렬 화면에서 문서 화면으로 전환

정렬 화면에서 이슈 버튼을 누를 때는 다음 순서를 지킨다.

1. 이슈 ID로 `ReviewIssue`를 조회한다.
2. 검수 패널 열기 요청과 에디터 이동 요청을 같은 이벤트에서 생성한다.
3. 문서 모드로 전환한다.
4. `requestAnimationFrame` 또는 동등한 렌더 완료 시점까지 기다린다.
5. 양쪽 에디터의 현재 DOM과 scroll container를 다시 조회한다.
6. 앵커를 계산하고 스크롤한다.
7. 검수 패널이 마운트된 뒤 해당 카드의 내부 목록 이동 요청을 소비한다.

정렬 오버레이가 `visibility: hidden`인 동안에는 `getBoundingClientRect()` 결과를 기준으로 삼지 않는다. 문서 모드 전환 전 좌표를 캐시해서 사용하지도 않는다.

### 5.4 일반 이슈의 앵커 선택

일반 이슈에 대해 각 패널에서 다음 순서로 앵커를 찾는다.

#### 번역문 패널

1. `targetExcerpt`가 비어 있지 않으면 해당 이슈의 `segmentGroupId` 또는 알고 있는 unit 범위 안에서 `findExcerptRange()`를 실행한다.
2. 고유한 exact range를 찾으면 `exact-range`를 사용한다.
3. exact range가 없고 대응 target unit을 확실히 찾을 수 있으면 `unit-range`를 사용한다.
4. 모호하거나 전역에서 여러 번 일치하면 이동하지 않는다.

#### 원문 패널

1. `sourceExcerpt`가 비어 있지 않으면 동일한 방식으로 exact range를 찾는다.
2. source exact range가 없으면 target에서 확인한 단위 또는 `findAlignedCounterpartUnits()`로 대응 source unit을 찾는다.
3. 대응 매핑이 완전하지 않거나 모호하면 이동하지 않는다.

양쪽에 발췌문이 모두 있고 두 exact match가 모두 성공하면 대응 매핑보다 두 exact match를 우선한다. 한쪽 exact와 다른 쪽 unit fallback이 함께 성공하는 경우도 허용하지만, 서로 다른 단위를 가리키는지 확인할 수 없으면 fallback을 사용하지 않는다.

### 5.5 누락·추가 이슈

#### 원문만 존재하는 경우

`targetExcerpt`가 비어 있으면 원문 `sourceExcerpt`를 기준으로 exact match를 시도한다. 번역문은 다음 경우에만 이동한다.

- 원문이 속한 translation unit과 대응하는 target unit을 확실히 찾은 경우
- 대응 target unit이 유일하고 LCS/ID 매핑이 fail-closed 조건을 통과한 경우

번역문 전체의 임의 위치나 마지막으로 선택된 문장으로 이동하지 않는다.

#### 번역문만 존재하는 경우

`sourceExcerpt`가 비어 있으면 번역문 `targetExcerpt`를 기준으로 exact match를 시도한다. 원문은 확실한 source counterpart가 있을 때만 이동한다.

#### 완전 누락

대상 발췌문이 없고 대응 단위의 텍스트도 존재하지 않으면 반대 패널의 위치를 만들 수 없다. 이 경우 이동 가능한 한쪽만 이동하고, 자동 적용 로직에서 사용하는 것처럼 위치를 추측하지 않는다.

### 5.6 스크롤 보정

스크롤은 `scrollIntoView()`에 의존하지 않는다. 중첩 컨테이너, 포커스에 의한 예상치 못한 이동, 전역 zoom 때문에 현재 구조에서 직접 계산하는 편이 안전하다.

개념적인 계산은 다음과 같다.

```text
anchorRect = 앵커 시작 위치의 화면 좌표
containerRect = 해당 ProseMirror 스크롤 컨테이너의 화면 좌표
visualDelta = anchorRect.top - containerRect.top - topGap
scrollDelta = visualDelta / editorZoom
nextTop = clamp(scrollTop + scrollDelta, 0, scrollHeight - clientHeight)
container.scrollTo({top: nextTop, behavior: 'smooth'})
```

구현 시 주의사항:

- `topGap`은 패널 상단 경계와 앵커가 완전히 붙지 않도록 작은 고정 여백으로 둔다. 기본 후보는 8~12 CSS px이며 실제 UI를 보고 하나로 고정한다.
- `coordsAtPos(range.from)`가 가능하면 텍스트 범위의 시작 좌표를 사용한다.
- 범위 좌표를 얻지 못하면 해당 translation unit의 `data-translation-unit-id` DOM 요소 상단을 fallback으로 사용한다.
- 현재 보이는 앵커인지 여부와 무관하게 전체 문서에서 위치를 계산한다. 단, DOM이 없는 숨겨진 패널은 스크롤하지 않는다.
- 화면에 앵커가 이미 상단에 있으면 불필요한 scroll 이벤트를 발생시키지 않는다.
- `editorZoom`은 화면 좌표를 콘텐츠 스크롤 좌표로 바꾸는 단계에서 반영한다.
- 소스와 타깃의 글꼴·줄 높이·너비 차이는 보정해서 같게 만들 대상이 아니다. 각 패널의 실제 좌표를 그대로 사용한다.
- 부드러운 이동은 사용자 경험용이며, 테스트에서는 이동 완료 후 좌표가 허용 오차 안에 있는지를 검증한다.

## 6. 권장 구현 구조

### 6.1 순수 위치 결정 유틸리티

새 유틸리티를 별도 파일로 둔다. 후보 경로는 `src/editor/utils/reviewIssueNavigation.ts`다.

이 모듈은 React나 전역 store에 의존하지 않고 다음 책임만 가진다.

1. `ReviewIssue`와 양쪽 ProseMirror 문서를 입력받는다.
2. 각 패널의 `IssueAnchor`를 계산한다.
3. exact range, unit fallback, 대응 단위 매핑의 우선순위를 적용한다.
4. ambiguous/partial mapping을 `none`으로 처리한다.
5. 실제 DOM 스크롤은 별도 함수 또는 얇은 어댑터로 분리한다.

권장 타입의 개념은 다음과 같다. 실제 이름은 기존 프로젝트 명명 규칙에 맞춘다.

```ts
type ReviewAnchorKind = 'exact-range' | 'unit-range' | 'none'

interface ReviewIssueAnchor {
  side: 'source' | 'target'
  kind: ReviewAnchorKind
  range?: {from: number; to: number}
  unitId?: string
  confidence: 'exact' | 'counterpart' | 'none'
}

interface ReviewIssueNavigation {
  issueId: string
  source: ReviewIssueAnchor
  target: ReviewIssueAnchor
  primarySide: 'source' | 'target'
}
```

새 유틸리티는 `resolveSuggestionRange()`의 suggested fix 기반 fuzzy 동작을 무조건 재사용하지 않는다. 위치 이동에 필요한 텍스트는 `sourceExcerpt`와 `targetExcerpt`이며, 적용 대상의 새 텍스트 길이가 위치를 결정하게 해서는 안 된다.

### 6.2 실제 에디터 스크롤 어댑터

같은 모듈 또는 인접한 모듈에 다음 책임을 둔다.

- Tiptap `Editor`/`EditorView`에서 실제 `.ProseMirror` scroll container를 얻는다.
- `IssueAnchor`의 range 또는 unit ID를 DOM 좌표로 변환한다.
- zoom과 top gap을 반영하여 `scrollTo`를 호출한다.
- 에디터가 마운트되지 않았거나 읽기 전용 오버레이 뒤에 있으면 조용히 skip한다.

에디터 인스턴스나 React ref를 Zustand에 저장하지 않는다. 기존 editor store에서 인스턴스를 읽고, DOM ref는 컴포넌트 경계에서 전달한다.

### 6.3 공통 이동 오케스트레이터

검수 패널 카드와 정렬 화면 버튼이 서로 다른 위치 계산을 갖지 않도록 공통 이동 함수를 사용한다.

오케스트레이터의 입력:

- `issueId` 또는 완전한 `ReviewIssue`
- 현재 source/target editor 인스턴스
- 현재 문서 모드와 표시 중인 패널 정보
- `editorZoom`
- 이동 출처(`review-card`, `alignment-row`, `view-button` 등)

오케스트레이터의 책임:

1. 이슈가 여전히 미해결 목록에 있는지 확인한다.
2. 정렬 화면이면 문서 모드 전환을 요청한다.
3. 렌더 프레임 이후 순수 resolver를 실행한다.
4. 표시 중인 각 패널에 대해 독립적으로 스크롤한다.
5. 결과가 한쪽만 성공했는지, 모두 실패했는지 구분한다.
6. 필요한 경우 검수 카드 스크롤 요청을 남긴다.

이동 출처에 따른 차이는 오케스트레이터가 아니라 호출부의 부수 동작으로 둔다. 예를 들어 정렬 행 버튼만 `openReviewPanelForIssue`를 추가로 호출하고, 이슈 카드의 `본문에서 보기`는 이미 열린 검수 패널을 유지한다.

### 6.4 마운트 전 검수 카드 이동 요청

정렬 화면에서 검수 패널을 열면서 특정 카드까지 이동해야 하므로 일회성 요청 상태를 둔다.

권장 방식:

- `uiStore`에 `pendingReviewIssueNavigation`을 추가한다. `openReviewPanel`이 UI 레이아웃을 소유하고 있기 때문이다.
- 상태에는 `issueId`, `requestId` 또는 증가하는 nonce, 요청 출처 정도만 저장한다.
- 에디터 인스턴스, DOM 노드, 함수는 저장하지 않는다.
- `partialize`에 포함하지 않아 앱 재시작 후 남지 않게 한다.
- 동일한 이슈를 연속으로 눌러도 처리되도록 매번 새로운 `requestId`를 발급한다.
- `ReviewPanel` 마운트 후 effect에서 요청을 소비하고, 내부 카드 목록 scroll container에서 `data-issue-id`를 찾는다.
- 처리 완료 또는 대상 카드를 찾지 못한 후 요청을 소비하여 stale request가 남지 않게 한다.

대안으로 review store에 같은 transient request를 둘 수 있지만, 패널 열기와 마운트 수명주기가 UI store에 이미 있으므로 이번 기능에서는 UI store를 우선 검토한다.

### 6.5 ReviewResultsTable 내부 스크롤

검수 패널에는 바깥쪽 패널 스크롤과 이슈 목록 안쪽 스크롤이 모두 존재한다. 카드 이동은 반드시 실제 카드 목록 스크롤 컨테이너를 대상으로 한다.

- 목록 컨테이너에 ref를 둔다.
- 카드에 `data-issue-id`를 둔다.
- 카드 이동은 `card.offsetTop - list.offsetTop - cardTopGap` 방식 또는 카드/목록의 `getBoundingClientRect()` 차이로 계산한다.
- 목록을 `scrollIntoView()`에 맡겨 바깥 패널까지 움직이지 않도록 한다.
- 검수 패널 자체가 화면 밖에 있으면 필요 시 바깥 패널은 현재 구현의 일반 레이아웃 흐름에 맡기되, 이번 기능에서 두 스크롤을 연쇄적으로 강제하지 않는다.

## 7. 상태와 데이터 일관성

### 7.1 이슈 ID를 단일 식별자로 사용

새 기능을 위해 `ReviewIssue` 스키마나 백엔드 응답 형식을 변경하지 않는다. 현재 deterministic `issue.id`를 카드, annotations, 정렬 행 버튼, pending request 간의 공통 키로 사용한다.

### 7.2 해결된 이슈 제외

정렬 화면 배지와 이동 대상은 검수 패널에서 실제로 선택 가능한 미해결 이슈와 같은 집합을 사용해야 한다.

- annotations 계산에서 `results.flatMap(...)` 전체를 직접 사용하지 않는다.
- `getAllIssues()`와 동일한 resolved filtering/deduplication을 적용한다.
- 이슈가 해결되는 순간 해당 행의 개수와 `issueIds`가 함께 갱신되어야 한다.
- 이미 해결된 이슈를 pending request로 받았을 때는 이동하지 않고 요청을 소비한다.

### 7.3 심각도 필터

심각도 필터는 사용자의 현재 목록 표시 설정이다. 이슈 위치 이동 때문에 자동으로 필터를 바꾸지 않는다.

- 정렬 행 배지의 집계는 미해결 이슈 전체를 기준으로 한다.
- 집계 버튼이 선택한 첫 이슈가 현재 필터에 의해 숨겨질 수 있다.
- 이 경우 에디터 이동은 수행한다.
- 검수 카드 이동은 대상 카드가 DOM에 있는 경우에만 수행한다.
- 필터를 잠깐 해제하거나 자동으로 변경하는 것은 이번 범위에 포함하지 않는다.

이 정책이 혼동을 일으키는지 사용성 테스트에서 확인하고, 필요하면 후속으로 “필터에 보이는 이슈 중 첫 번째”를 선택하는 옵션을 검토한다.

## 8. 패널 너비가 다른 경우의 정책

### 8.1 너비 차이의 성격

패널 너비가 다르면 같은 텍스트도 줄바꿈 위치와 전체 높이가 달라진다. 또한 언어별 글자 폭, 글꼴, 줄 높이, 표 셀 구조, 이미지·위젯 유무가 달라서 원문과 번역문의 전체 문서 좌표를 1:1로 맞추는 것은 원리적으로 불가능하다.

그러나 이슈 앵커를 각 패널의 상단으로 보내는 것은 가능하다. 너비 차이는 “같은 `scrollTop`으로 맞추는 방식”의 한계이지, “각 패널의 앵커를 상단에 두는 방식”의 한계가 아니다.

### 8.2 현재 위치 맞춤의 어긋남과 구분

현재 `위치 맞춤`이 패널 너비 차이 때문에 살짝 어긋나 보일 수는 있지만, 다음 요인도 함께 확인해야 한다.

- 같은 `scrollTop`을 사용하고 있는지
- 실제 scroll container와 측정한 DOM 요소가 같은지
- 문서 모드 전환 직후 측정했는지
- smooth scroll 도중에 캡처했는지
- 전역 zoom을 보정했는지
- 앵커의 현재 보이는 부분이 아니라 단위 전체의 시작점을 사용했는지
- source/target의 상단 padding, toolbar, margin이 다른지

따라서 이번 기능은 너비 차이를 이유로 대충 상대 위치를 복사하지 않고, 각 패널의 실제 앵커 좌표를 직접 계산한다.

### 8.3 너비 동일화 기능을 이번 범위에 포함할지

핵심 이슈 이동에는 포함하지 않는다. 이유는 다음과 같다.

- 사용자가 조정한 패널 폭은 개인의 편집 레이아웃 선호일 수 있다.
- 이슈 클릭마다 50:50으로 바꾸면 레이아웃이 갑자기 변한다.
- 현재 `PanelGroup`은 기본 크기만 지정하고 사용자의 실시간 크기를 제어하는 API/ref 구조가 별도다.
- 폭을 같게 해도 언어별 줄바꿈·글꼴 차이는 남는다.

다만 비교 작업을 위해 다음과 같은 별도 기능은 유용하다.

> `양 패널 너비 동일` 또는 `비교 폭 맞춤` 토글

별도 기능으로 구현할 경우의 조건:

- 원문과 번역문이 모두 표시될 때만 활성화한다.
- 활성화 시 두 패널을 50:50 또는 사용자가 정한 동일 비율로 맞춘다.
- 토글 전의 사용자 패널 폭을 임시로 기억하고 해제 시 복원한다.
- 이슈 클릭 시 자동 발동하지 않는다.
- 사용자가 명시적으로 켠 경우에만 적용한다.
- 이번 구현에서 `PanelGroup` 제어 API를 함께 건드리지 않는다.

## 9. 실패·예외 처리 정책

| 상황 | 기대 동작 |
| --- | --- |
| source exact만 성공 | 원문만 이동하고 번역문은 추측하지 않음 |
| target exact만 성공 | 번역문만 이동하고 원문은 추측하지 않음 |
| 양쪽 exact 성공 | 양쪽을 각자 이동 |
| 한쪽 exact + 다른 쪽 대응 unit 성공 | 두 위치를 이동하되 대응 매핑이 확실할 때만 허용 |
| 대응 unit이 부분 매핑 | 대응 패널은 이동하지 않음 |
| 발췌문이 문서에 여러 번 등장 | unit 범위로 고유하게 좁혀지지 않으면 이동하지 않음 |
| editor instance가 아직 준비되지 않음 | 오류 없이 skip, 기존 not-ready 안내 또는 localized 안내 사용 |
| 정렬 화면이 아직 문서 DOM으로 전환되지 않음 | 한 프레임 뒤 재시도, 무한 재시도 금지 |
| issue가 이미 resolved 됨 | pending 요청을 소비하고 이동하지 않음 |
| 심각도 필터로 카드가 숨겨짐 | 필터를 바꾸지 않고 에디터만 이동 |
| 한 패널만 보이는 모드 | 보이는 패널만 이동 |
| 문서가 변경되어 stale excerpt가 됨 | 고유 매칭이 불가능하면 이동하지 않음 |

위치 특정 실패는 기능 전체의 오류로 처리하지 않는다. 잘못된 위치로 이동하는 것보다 현재 위치를 유지하는 것이 안전하다. 사용자가 이유를 알아야 하는 경우에는 기존 `review.viewNotFound` 계열 메시지를 재사용하거나 다음과 같은 새 i18n 키를 추가한다.

- `review.issuePositionNotFound`
- `review.issueCounterpartPositionNotFound`
- `review.navigateIssue`
- `editor.alignment.viewIssue`

새 UI 문구가 추가되면 반드시 한국어와 영어 번역을 모두 추가한다.

## 10. 예상 부작용과 완화책

| 위험 | 영향 | 완화책 |
| --- | --- | --- |
| 잘못된 scroll container 선택 | 패널이 아닌 페이지가 움직이거나 위치가 어긋남 | 실제 `.ProseMirror`와 computed overflow를 확인하고 전용 ref 사용 |
| 양쪽에 같은 scrollTop 적용 | 폭·줄바꿈 차이로 엉뚱한 문장이 보임 | source/target 좌표를 독립 계산 |
| zoom 미보정 | 확대/축소 상태에서 상단 오프셋 발생 | `editorZoom`을 delta 변환에 반영하고 zoom별 테스트 |
| 정렬 오버레이에서 좌표 측정 | 숨겨진 DOM 좌표가 부정확함 | 문서 모드 전환 후 requestAnimationFrame에서 측정 |
| 검수 패널 미마운트 | 정렬 화면에서 카드 이동 요청 유실 | nonce가 있는 transient pending request 사용 |
| filter 자동 변경 | 사용자의 목록 설정이 예기치 않게 변경됨 | filter 유지, 카드가 숨겨진 경우 카드 이동만 skip |
| resolved 이슈가 배지에 남음 | 클릭해도 존재하지 않는 카드로 이동 | annotations와 review list 모두 동일한 unresolved source 사용 |
| 중복 발췌문 오매칭 | 다른 문장으로 이동 | unit 범위와 고유성 확인, 모호하면 fail-closed |
| 행 클릭과 이슈 버튼 충돌 | 이슈 버튼 클릭 시 행 선택까지 실행 | 버튼에서 `stopPropagation()` |
| smooth scroll 테스트 불안정 | 간헐적 E2E 실패 | unit 테스트는 직접 계산, E2E는 이동 완료 대기와 좌표 허용 오차 사용 |
| 사용자 패널 폭 강제 변경 | 편집 레이아웃이 갑자기 바뀜 | 핵심 기능에서 폭 자동 조정 금지 |
| 기존 위치 맞춤 회귀 | 선택 단위 동기화 동작 변경 | 기존 함수의 후보 제한과 테스트를 유지하고 새 이슈 이동과 분리 |

## 11. 테스트 계획

### 11.1 순수 유틸리티 단위 테스트

새 navigation resolver와 scroll 계산 함수에 다음 케이스를 추가한다.

- target exact match가 source exact match보다 의미상 기준이 되는 일반 이슈
- source와 target exact match가 모두 성공하는 일반 이슈
- target 발췌문이 비어 있는 원문 누락 이슈
- source 발췌문이 비어 있는 번역문 추가 이슈
- translation unit ID 직접 대응
- ID 대응이 없을 때의 정상 LCS 대응
- 부분 LCS/모호한 대응의 fail-closed
- 같은 발췌문이 여러 번 등장하는 경우
- `segmentGroupId` 범위 안에서는 고유하고 문서 전체에서는 중복인 경우
- exact match를 fuzzy/unit fallback보다 우선하는 경우
- `coordsAtPos` 실패 시 unit DOM fallback
- `editorZoom` 0.5, 1, 2에서의 delta 계산
- 문서 시작/끝에서 scrollTop clamp
- 이미 top gap 안에 있는 경우 불필요한 scroll 호출을 하지 않는 경우

### 11.2 annotations 테스트

`useAlignmentAnnotations` 또는 그 순수 계산 함수에 다음을 검증한다.

- 행별 issue count와 issueIds가 일치함
- issueIds가 문서 순서로 안정적임
- resolved issue가 count와 issueIds에서 제외됨
- 매칭되지 않은 이슈가 `unmappedIssueCount`로만 집계되고 임의 행에 붙지 않음
- 한 행에 여러 이슈가 연결되면 첫 번째 이동 대상이 결정적으로 선택됨

### 11.3 컴포넌트 테스트

`AlignmentRow`:

- 이슈 버튼이 렌더링됨
- `aria-label`이 번역 키를 통해 표시됨
- 클릭 시 해당 행의 첫 issue ID를 전달함
- 클릭 시 행 선택 콜백은 호출되지 않음
- 키보드 Enter/Space가 동일하게 동작함

`ReviewResultsTable`:

- 카드에 `data-issue-id`가 있음
- 카드 클릭이 해당 issue ID로 navigation callback을 호출함
- 적용/복사/무시/체크박스 조작이 카드 navigation을 호출하지 않음
- 목록 내부 ref를 사용해 대상 카드가 보이도록 함
- 필터로 숨겨진 카드는 목록 이동 대상이 되지 않음

`ReviewPanel`:

- reviewing 분기와 completed 분기 모두 navigation callback을 전달함
- 마운트 전 pending request가 카드 목록이 마운트된 후 소비됨
- 같은 issue ID를 연속 요청해도 requestId가 달라 처리됨
- 없는 issue ID나 resolved issue 요청은 안전하게 소비됨

### 11.4 E2E/실제 레이아웃 테스트

실제 Tauri/브라우저 환경에서 다음을 검증한다. 기존 `e2e/alignment-view.spec.ts`의 모드 전환 시나리오를 확장하는 것을 우선 검토한다.

1. 검수 이슈가 연결된 정렬 행에서 이슈 버튼이 보인다.
2. 이슈 버튼을 누르면 문서 화면으로 전환된다.
3. source와 target의 실제 scroll container가 모두 움직인다.
4. 각 패널의 앵커 상단이 패널 상단 여백 안에 들어온다.
5. 검수 패널이 열리고 해당 카드가 목록에서 보인다.
6. source/target 폭을 다르게 했을 때도 두 앵커가 각각 상단에 온다.
7. 긴 번역문으로 줄바꿈 수가 달라도 같은 이슈가 유지된다.
8. 누락 이슈는 존재하는 쪽으로만 안전하게 이동한다.
9. 모호한 발췌문은 엉뚱한 문장으로 이동하지 않는다.
10. 포커스/단일 패널 모드에서 숨겨진 패널을 강제로 열지 않는다.

E2E fixture는 production 코드에 디버그용 상태 주입 API를 추가하지 않는다. 기존의 테스트 시드/fixture 주입 경로를 사용하고, 기존 경로가 없으면 테스트 전용 helper를 별도로 만든다.

## 12. 구현 단계

### 단계 0 — 구현 전 확인

- 현재 브랜치의 관련 파일과 테스트를 다시 확인한다.
- 작업 트리에 이미 존재하는 사용자 변경을 건드리지 않는다.
- 기존 `위치 맞춤` 동작을 새 기능의 성공 기준으로 재정의하지 않는다.
- 새 i18n 문구가 필요한지 먼저 확정한다.

### 단계 1 — 앵커 resolver와 스크롤 계산

- `reviewIssueNavigation` 계열 순수 타입과 resolver를 추가한다.
- 기존 `findExcerptRange`, `findAlignedCounterpartUnits`, translation unit 수집 로직을 재사용한다.
- `resolveSuggestionRange`의 suggested fix 의존성을 위치 이동 경로에서 제거한다.
- source/target 양쪽 방향의 대응 매핑을 지원한다.
- zoom, top gap, clamp를 처리하는 스크롤 어댑터를 추가한다.
- 먼저 단위 테스트를 작성하고 실패를 확인한 뒤 구현한다.

완료 기준: DOM과 React 없이 정상/누락/모호/부분 매핑의 위치 결정 결과를 예측할 수 있다.

### 단계 2 — 정렬 annotations와 이슈 버튼

- annotations에 `issueIds`를 추가한다.
- 해결된 이슈를 제외하도록 데이터 원천을 통일한다.
- `AlignmentView → AlignmentRow`로 navigation callback을 전달한다.
- 이슈 배지를 접근 가능한 버튼으로 만들고 행 클릭과 이벤트를 분리한다.
- 단위/컴포넌트 테스트를 통과시킨다.

완료 기준: 정렬 화면에서 클릭할 이슈 ID가 항상 결정되고, 행 선택 회귀가 없다.

### 단계 3 — 양 패널 이동과 검수 카드 연결

- 공통 오케스트레이터를 `ReviewPanel`과 `EditorCanvasTipTap`의 진입점에 연결한다.
- 문서 모드 전환 후 한 프레임을 기다리는 lifecycle을 넣는다.
- source/target editor를 각각 조회하여 독립적으로 이동한다.
- 카드에 `data-issue-id`와 카드 이동 동작을 추가한다.
- `pendingReviewIssueNavigation`과 requestId 기반 consume effect를 추가한다.
- 검토 중/완료 화면의 모든 `ReviewResultsTable` 분기에 콜백을 전달한다.
- 실패·필터·단일 패널 모드 정책을 적용한다.

완료 기준: 카드와 정렬 버튼이 같은 navigation 경로를 사용하고, 어느 진입점에서도 양쪽 앵커 정책이 다르지 않다.

### 단계 4 — 실제 레이아웃 검증과 안정화

- 서로 다른 패널 너비, zoom, 긴 문장, 표 셀, 다중 노드 문서에서 확인한다.
- 기존 `위치 맞춤`과 이슈 이동이 서로 간섭하지 않는지 확인한다.
- 부드러운 이동 중 중복 클릭과 빠른 연속 클릭의 마지막 요청 처리 방식을 확정한다.
- 필요한 안내 문구와 접근성 속성을 보완한다.

### 단계 5 — 선택 과제: 패널 너비 동일화

핵심 기능이 안정화된 후 별도 이슈로 진행한다.

- `PanelGroup` 제어 방식과 사용자 크기 복원 가능성을 조사한다.
- 50:50 동일화 토글의 위치와 상태 수명을 설계한다.
- 명시적 사용자 동작에서만 적용한다.
- 이 기능을 이슈 클릭의 암묵적 부작용으로 연결하지 않는다.

## 15. 구현하지 않을 것

이번 계획은 다음을 포함하지 않는다.

- 이슈 이동을 위해 backend/API 응답 스키마 변경
- `ReviewIssue` ID 형식 변경
- 검수 결과 저장 형식 변경
- 이슈 클릭마다 패널 너비를 50:50으로 강제
- 원문과 번역문의 전체 문서 스크롤 위치를 항상 동일하게 유지
- 모호한 발췌문을 휴리스틱으로 임의 선택
- 숨겨진 패널을 사용자의 동의 없이 자동으로 다시 열기
- 정렬 행에서 여러 이슈를 개별 표시하는 새로운 복잡한 UI
- 기존 `위치 맞춤`의 목적과 동작을 이슈 이동에 맞춰 전면 재작성

## 16. 구현 모델을 위한 핵심 요약

구현자는 다음 네 문장을 기준으로 판단하면 된다.

1. **한 이슈에 하나의 공통 issue ID를 사용하고, source/target에는 서로 다른 앵커를 계산한다.**
2. **번역문을 의미상의 기본 기준으로 삼되, 실제 scrollTop은 양쪽 패널에서 독립적으로 계산한다.**
3. **정확한 매칭이 없거나 대응이 모호하면 이동하지 않으며, 잘못된 위치로 추측하지 않는다.**
4. **패널 너비 동일화는 핵심 이동 기능의 전제조건이 아니며 별도 명시적 옵션으로 미룬다.**
